# Cinema API

Серверна частина кінотеатру на NestJS: фільми, зали, сеанси та бронювання місць.
Дані зберігаються в MongoDB через Mongoose. Сервіс працює з трьома колекціями: `films`, `halls`, `showings`.

## Вимоги

- Node.js 22.22.3+ або 24.15.0+ (цього вимагає `@nestjs/cli`; на старіших версіях `npm install` покаже попередження `EBADENGINE`)
- Docker з Docker Compose

## Запуск

```bash
# 1. Встановити залежності
npm install

# 2. Створити .env з прикладу (див. розділ «Змінні оточення»)
cp .env.example .env

# 3. Підняти MongoDB через Docker Compose
docker compose up -d

# 4. Засіяти базу даними для перевірки (необов'язково)
npm run seed

# 5. Запустити в режимі розробки
npm run start:dev
```

Swagger-документація: http://localhost:3000/docs

## Змінні оточення

Файл `.env` не потрапляє до репозиторію. Приклад (`.env.example`):

```env
PORT=3000
NODE_ENV=development
MONGODB_URI=mongodb://cinema:cinema@localhost:27017/cinema?authSource=admin
CINEMA_TIMEZONE=Europe/Kyiv

# Лише для docker-compose.yml: користувач MongoDB, який створюється при першому запуску
MONGO_PORT=27017
MONGO_ROOT_USERNAME=cinema
MONGO_ROOT_PASSWORD=cinema
```

| Змінна | Опис |
| ------ | ---- |
| `PORT` | Порт HTTP-сервера |
| `NODE_ENV` | `development`, `production` або `test` |
| `MONGODB_URI` | Рядок підключення до MongoDB. `authSource=admin` потрібен, бо образ `mongo` створює кореневого користувача в базі `admin` |
| `CINEMA_TIMEZONE` | Часовий пояс кінотеатру (IANA), у ньому рахується доба для фільтра `date` |
| `MONGO_PORT`, `MONGO_ROOT_USERNAME`, `MONGO_ROOT_PASSWORD` | Порт і користувач контейнера MongoDB; їх читає лише Docker Compose. Мають збігатися з тими, що в `MONGODB_URI` |

Конфігурація застосунку проходить валідацію під час старту (`src/config/environment-variables.ts`): якщо змінної бракує або вона має неправильний формат, застосунок не запускається.
Підключення створює `MongooseModule.forRootAsync`, який бере `MONGODB_URI` з `ConfigService`.

> Користувач MongoDB створюється лише при першому запуску контейнера з порожнім томом. Щоб змінити ім'я чи пароль, видаліть том: `docker compose down -v`.

## Засівання

```bash
npm run seed
```

Скрипт `src/seed.ts` додає 2 фільми, 2 зали, 4 сеанси в різні дні (від завтра) та 1 бронювання на 2 місця.
Документи мають фіксовані `_id` і записуються через upsert з `$setOnInsert`, тому повторний запуск не створює дублікатів.

## Перевірка роботи

Файл `requests.http` містить запити до всіх маршрутів і до кожної описаної помилки.
Виконуйте їх згори вниз у VS Code з розширенням [REST Client](https://marketplace.visualstudio.com/items?itemName=humao.rest-client).
Ідентифікатори підставляються з відповідей попередніх запитів. Назви залів отримують мітку часу, тому файл можна проходити повторно.

## Тести

```bash
npm test           # unit-тести
npm run test:e2e   # e2e-тести всіх маршрутів
```

E2E-тести потребують піднятого контейнера (`docker compose up -d`) і `.env`. Вони працюють з окремою базою `cinema_test` на тому ж сервері й видаляють її після прогону, дані розробки не чіпають.

## Модель даних

| Колекція | Вміст |
| -------- | ----- |
| `films` | `title`, `durationMinutes`, `releaseYear` |
| `halls` | `name` (унікальний індекс), `rows`, `seatsPerRow`; перелік місць не зберігається, сервіс обчислює його з розмірів |
| `showings` | `film` і `hall` (ObjectId-посилання), `startsAt`, `price`, масив `seats` (`row`, `seat`, `bookingId`) і масив `bookings` (`_id`, `seats`, `totalPrice`, `createdAt`) |

Кожна колекція описана класом з `@Schema` і `@Prop`, вкладені документи (`ShowingSeat`, `Booking`, `BookedSeat`) — окремими класами зі своїми схемами.
Масив `seats` заповнюється під час створення сеансу з `rows` і `seatsPerRow` залу, усі місця вільні (`bookingId: null`).

### Чому місця й бронювання лежать усередині документа сеансу

Бронювання складається з двох дій: позначити місця зайнятими й зберегти запис бронювання.
У MongoDB неподільним є оновлення одного документа. Зміна кількох документів однією операцією вимагає транзакції, а транзакція вимагає replica set.
Якби бронювання й місця жили в окремих колекціях, між перевіркою вільних місць і записом інший запит міг би зайняти те саме місце, і без транзакції це нічим не захищено.

Тому місця й бронювання вкладені в документ сеансу, і бронювання виконується одним `updateOne`:

- фільтр через `$and` з `$elemMatch` пропускає документ лише тоді, коли кожне потрібне місце має `bookingId: null`;
- `$set` з позиційним оператором `seats.$[target]` і `arrayFilters` проставляє `bookingId` у потрібні місця;
- `$push` у тому ж оновленні додає запис до `bookings`;
- якщо хоч одне місце зайняте, фільтр нічого не знаходить, документ не змінюється, `matchedCount` дорівнює 0, і сервіс повертає 409.

Два одночасні запити на те саме місце виконуються послідовно: другий отримає `matchedCount: 0`.
Скасування так само одним оновленням знаходить сеанс за `bookings._id`, повертає `null` у місця (`$set` + `arrayFilters`) і видаляє запис (`$pull`).

Межі застосовності: вкладення підходить, бо кількість даних обмежена. Місць у залі не більше 100 × 100, бронювань на сеанс не більше, ніж місць, тому документ сеансу не росте безмежно.
Фільм і зал, навпаки, спільні для багатьох сеансів, тому лежать в окремих колекціях, а сеанс посилається на них через ObjectId і розкриває назви через `populate`.

Масив `seats` — джерело істини про зайнятість. Перелік місць у записі бронювання дублює його, щоб віддати бронювання без перебору всіх місць залу.

## Структура

| Модуль | Відповідальність |
| ------ | ---------------- |
| `films` | CRUD фільмів |
| `halls` | зали, обчислення переліку місць з `rows` і `seatsPerRow` |
| `showings` | сеанси, розклад з фільтрами, сортуванням і посторінковою видачею, зайнятість місць сеансу |
| `bookings` | бронювання й скасування одним оновленням документа сеансу, перелік бронювань |

Моделі підключаються у feature-модулях через `MongooseModule.forFeature`. `ShowingsModule` експортує модель сеансів для `BookingsModule`, бо бронювання живуть у документах сеансів.
`films` і `halls` перевіряють залежні сеанси перед видаленням, а `showings` перевіряє існування фільму й залу, тому ці модулі пов'язані через `forwardRef`.

## Поведінка API

- Ідентифікатори мають формат ObjectId (24 шістнадцяткові символи). Некоректний формат у параметрі маршруту, у фільтрі `filmId` або в тілі (`filmId`, `hallId`) дає 400 до звернення до бази; коректний, але неіснуючий id — 404.
- У відповідях `_id` віддається рядковим полем `id`; документи перетворюються на відповідь класами DTO (`FilmDto`, `HallDto`, `ShowingDto`, `ShowingViewDto`, `BookingViewDto`).
- `GET /showings` повертає `{ items, total, page, limit, totalPages }`. Параметри: `filmId`, `date` (YYYY-MM-DD), `page` (від 1, за замовчуванням 1), `limit` (1–100, за замовчуванням 20), `sort` (`asc`/`desc`, за замовчуванням `asc`). Фільтр, `sort`, `skip` і `limit` виконує MongoDB, сеанси з однаковим часом упорядковані за `_id`.
- `GET /showings` і `GET /showings/:id` повертають `filmTitle` і `hallName` (через `populate`) без масивів `seats` і `bookings`. `POST /showings` повертає `filmId` і `hallId`, теж без масивів.
- `GET /bookings` збирає бронювання з усіх сеансів агрегацією (`$unwind` масиву `bookings`).
- Межі залу й унікальність місць у запиті перевіряються до оновлення: місце поза залом чи повтор дають 400, а не 409.
- Видалення фільму чи залу, на який посилається сеанс, дає 409. Зовнішніх ключів у MongoDB немає, тому сервіс перевіряє це запитом.
- Усі помилки мають єдину структуру: `{ statusCode, timestamp, path, message }`.
- `startsAt` приймається в розширеному форматі ISO 8601 з датою й часом і повертається в UTC.
- Цілі поля (тривалість, рік, ціна) обмежені 2 147 483 647; розмір залу — до 100 рядів і до 100 місць у ряду.
